## [CWE-639] User-owned routes trusted a user id supplied in the request body (V3)

Branch for this work: `fix/Imaadh-V3-owner-checks`.

- **Vulnerability:** Authorization Bypass Through User-Controlled Key (IDOR). Eighteen routes in `backend/routes/user.js` that act on user-owned data had **no authentication middleware at all** — only `PUT /uploadprofile` was guarded. Every one of their controllers then took the _actor_ identity from the request body: `const { postid, userid } = req.body` for the bookmark/like/post/report controllers, `const { about, id } = req.body` for `changeabout`, and `const { id, id2 } = req.body` for `follow`/`unfollow`/`checkfollowing`. Because the id was both unauthenticated and caller-supplied, any client could read or mutate **any** user's data by naming that user:
  - read a victim's private bookmarks and likes (`/getallBookmarks`, `/getallLikes`, `/showbookmarks`, `/showLikemarks`),
  - delete a victim's bookmark or like (`/deletebookmark`, `/deletelikes`),
  - add a bookmark or like "as" the victim (`/setbookmark`, `/setlikes`),
  - overwrite a victim's `about` text (`/changeabout`),
  - make a victim follow or unfollow someone (`/startfollow`, `/unfollow`),
  - file a content report as the victim (`/reportcontent`).
    `deletepost` was worse than the rest: it ran `Post.deleteOne({ _id: postid })` with **no ownership check on the post whatsoever**, so any authenticated user could permanently destroy anybody's post just by knowing its id. No token was required, and no comparison against the post's owner was ever made.

- **Fix applied:** Two layers, applied per route group.
  1. **Route layer** — `authUser` was added to all 18 routes, so a valid bearer token is now mandatory.
  2. **Controller layer** — the actor is no longer read from the body. The declared key was removed from every destructure and replaced with `req.user.id` from the verified JWT (e.g. `const { postid } = req.body;` plus `const userid = req.user.id;`). Where a route legitimately references a _different_ user, only the **target** id is still taken from the body and the actor is derived from the token — `follow`, `unfollow` and `checkfollowing` keep `id2` and take `id` from `req.user.id`.
  3. **`deletepost` needed more than the token.** Deriving the actor was not sufficient there, because the destructive operation targeted the post document rather than the caller's own array. It now loads the post, compares `post.user` against `req.user.id`, and returns **403** before deleting anything.
  4. **The client had to change too, and the brief did not mention it.** Only 4 of 40 helper functions in `client/src/helpers/index.js` sent an `Authorization` header, so adding auth to 18 routes would have broken roughly 36 calls across `Article.js`, `PostCard.js`, `UserProfile.js` and `ProfileOfOtherUser.js`. Rather than edit ~41 call sites, a **request interceptor** was added in `client/src/helpers/interceptor.js` (`setupAxiosInterceptors` already receives the Redux store) that attaches the bearer token to every outbound request and deliberately does **not** overwrite a caller-set header. One file changed instead of forty.
  5. Awaiting the security-critical writes: `bookmark`, `likes` and `deletepost` called `save()` without `await`, so the response could be sent before the change persisted and any failure escaped the surrounding `catch` as an unhandled rejection. Runs of the new test suite surfaced this; they are now awaited.

- **Security contribution:** The actor identity is now derived from a verified signature instead of a value the caller chooses, which removes the IDOR class entirely for these routes: there is no longer any code path where a supplied id decides whose data is written. Reads of private collections (`bookmarks`, `likes`, `following`) are now scoped to the authenticated user. Post deletion is ownership-checked on the resource itself, closing an unconditional destroy-any-post primitive that the token change alone would not have closed. Unauthenticated callers receive 401 on all 18 routes.

- **Justification:** The vulnerability was confirmed by reading the real code rather than assuming: grepping for `req.body.userid` finds nothing, because the id is destructured (`const { postid, userid } = req.body`) — the brief's implied search would have produced a false "not vulnerable". The four routes deliberately left public were verified as genuinely public rather than forgotten: `fetchprof`, `countfollower`, `countfollowing` and `getUser/:userId` read _another_ user's public profile data and are called from the public article page (`client/src/components/article/Article.js`), so requiring auth would break logged-out browsing — a test asserts they still work without a token. Regression evidence: `backend/tests/idor.test.js` runs 32 cases — one per protected route asserting 401 without a token, plus per-controller cases where an authenticated attacker supplies the _victim's_ id and the assertion is that the victim's data is untouched and the write lands on the attacker instead. `POST /deletepost` is asserted to return 403 and to leave the post document intact. Full backend suite: **38 passed, 2 suites** (`npm test`). This also finally executed the V14 suite from `tests/authRefresh.test.js`, which passes.

- **Observed — out of scope (recommended follow-up):** `getUser` in `backend/controllers/user.js` returns `const { password, ...otherdata } = user` for any `userId`, which exposes that user's `email`, `likes`, `bookmarks`, `likeslist` and `bookmarkslist` to any caller. It is a genuine over-exposure of another user's data, but the route reads public profile data by design and fixing it means whitelisting returned fields — a behaviour change to a public endpoint that deserves its own change set and tests. Flagged rather than silently included.

- **Observed — dead code (recommended deletion):** `showyourposts` in `backend/controllers/user.js` still destructures `const { id } = req.body` and is not registered on any route. It is unreachable today, but if it were ever wired up it would reintroduce exactly this vulnerability. Left untouched to keep this change set scoped.
