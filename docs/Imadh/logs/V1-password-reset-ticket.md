## [CWE-640] Password reset allowed unauthenticated password change and leaked account existence (V1)

Branch for this work: `fix/Imadh-V1-changepassword-token`.

- **Vulnerability:** The password-reset flow was authorisation-free from end to end.
  1. **`changePassword` accepted `{ email, password }` with no authentication, no reset code and no ticket.** A single anonymous POST naming any address overwrote that account's password hash. This is the critical finding: full account takeover of any registered user, with no prior access and no knowledge beyond an email address (CWE-620, Unverified Password Change). V15 had added password _strength_ validation here but explicitly left the missing authorisation to V1.
  2. **`sendResetPasswordCode` leaked whether an address was registered.** It dereferenced `user._id` without checking `user`, so an unknown address threw a `TypeError` — and the `catch` block returned `error.message` verbatim to the caller. A registered address failed differently (see item 4), so the two cases produced **distinguishable error messages**: an enumeration oracle. Note the mechanism precisely — fixing only the Mongoose bug would have converted this into a _status-code_ oracle instead (500 for unknown, 200 for known), so the uniform response was required as well, not just the null guard.
  3. **`validateResetCode` had the same null-dereference** (500 for an unknown email) and returned only `{ message: "ok" }` — no credential at all. That is precisely _why_ `changePassword` had to accept an email from the caller: there was nothing else to identify the user with.
  4. **The entire flow was already non-functional.** Both endpoints called `Code.findOneAndRemove()`, a method **removed in Mongoose 8**. It throws a `TypeError`, which the surrounding `catch` converted to a 500. So resetting a password failed for _every_ address, registered or not, before this change — discovered when the new tests 500'd on the happy path.

- **Fix applied:** The reset flow now hands out a signed, single-use, purpose-scoped ticket, and the password change is authorised by that ticket alone.
  - `backend/models/PasswordResetTicket.js` (new) records each issued ticket by `jti` with a TTL index on `expiresAt` and a `usedAt` flag — the same shape as the refresh-token store, so single-use rests on a database guarantee rather than on client behaviour.
  - `backend/helper/resetTicket.js` (new) provides `issueResetTicket` (a 32-byte random `jti`; a JWT carrying `userId`, `purpose: "password-reset"`, 5-minute expiry), `verifyResetTicket` (signature + purpose + expiry, **no side effect**) and `consumeResetTicket` (atomic `findOneAndUpdate({ jti, usedAt: null })`, so only the first caller can spend it).
  - `sendResetPasswordCode` now returns an identical body whether or not the address is registered, and the null dereference is gone.
  - `validateResetCode` returns one generic 400 for both "no such user" and "wrong code", mints the ticket on success, and deletes the emailed code so it cannot mint a second ticket.
  - `changePassword` takes `{ resetTicket, newPassword }` **only**. The email parameter is gone entirely; the target user comes from the ticket's signed `userId` claim. Ordering is verify → validate password → consume → write, so a password rejected by V15's policy does not burn the ticket.
  - `Code.findOneAndRemove` → `Code.findOneAndDelete` in both endpoints, which is what made the flow work at all.
  - On success every refresh token for the account is revoked via `revokeAllForUser` — the item the V12 task deferred to V1.

- **Security contribution:** The account-takeover primitive is gone: an attacker can no longer change a password without proving control of the mailbox, and no field in the request body can influence _whose_ password changes. Tickets are signed (unforgeable), purpose-scoped (a reset ticket cannot double as an access token), short-lived (5 minutes) and single-use (atomic compare-and-set, so a replay or a concurrent second request is rejected). The emailed code is also single-use, halving the window for a stolen code. Both reset endpoints return uniform responses, removing the enumeration oracle. A successful reset now terminates every existing session, so a stolen refresh token dies at the moment the password changes. As a side effect the flow is functional for the first time.

- **Justification:** Confirmed by reading the code before changing it: `changePassword` destructured `email` and called `User.findOneAndUpdate({ email }, ...)` with no middleware and no code comparison on the route (`backend/routes/user.js` registers it as a bare `router.post("/changePassword", changePassword)`), and `sendResetPasswordCode` dereferenced `user._id` before any null check. The `findOneAndRemove` defect was not assumed — it surfaced as three failing tests on the happy path and was then confirmed by the method being absent from Mongoose 8. Regression evidence: `backend/tests/passwordReset.test.js` adds 19 cases covering exactly the cases the brief requires — no ticket → 401, wrong purpose → 401, reused ticket → 401, expired ticket → 401 — plus forged-signature and unrecorded-`jti` tickets → 401, the old `{ email, password }` contract → 401, ticket-target cannot be redirected by a body email, the emailed code is single-use, `sendResetPasswordCode` responses are identical for known and unknown addresses, a weak password does not consume the ticket, and refresh tokens are revoked. Full backend suite: **52 passed, 3 suites**. V15's password policy is preserved and its `userInputs` are now fed the real name and email from the ticket's user rather than an unverified body value.

- **Observed — out of scope (recommended follow-up, listed in priority order):**
  1. **`findOutUser` returns the entire user document, including the bcrypt password hash, to any unauthenticated caller** (`res.status(200).json(user)`), and it is called by the reset UI itself. A hash disclosure is an offline-cracking target for every registered account. It also branches 404/400/200 in ways that enumerate accounts. Not fixed here because the reset page depends on its current shape; the minimum fix is `.select("-password")`.
  2. **`helper/gen_code.js` uses `Math.random()`**, which is not a cryptographically secure source, so emailed codes are predictable. It is shared with the email-verification OTP in `backend/controllers/verifyemail.js`. `crypto.randomInt` is the correct replacement.
  3. **No rate limiting** on `sendResetPasswordCode` or `validateResetCode`. A 5-digit code with unlimited attempts is brute-forceable within its 30-minute TTL; `express-rate-limit` would close this.
