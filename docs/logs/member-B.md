# Member B — Weekly Log

## Week 2 — V2: NoSQL injection in /login (CWE-943, OWASP A03:2021)

- Confirmed the vulnerability with a live PoC: sending `{"temail":{"$ne":null}}` to `POST /login` bypassed the email lookup — the query matched a real user and returned "Invalid Credentials" instead of "not registered", proving the injected operator object defeated authentication lookup. Raised issue #3.
- Applied defense in depth: added `express-mongo-sanitize` as global middleware in `backend/index.js` (strips `$`/dotted keys) and a `zod` schema (`backend/validators/login.schema.js`) forcing `temail`/`password` to be strings, rejecting bad input with 400 before the DB query runs.
- Justified two layers: the sanitizer alone still lets non-string types (`temail:12345`, arrays) reach the query; zod closes that gap. Verified this experimentally.
- Set up the backend's first test suite (Jest + supertest) and wrote 6 regression tests in `backend/tests/login.injection.test.js`; confirmed 5/6 fail on pre-fix code and 6/6 pass after (red/green evidence).
- Captured before/after PoC output (`docs/scans/v2-poc-before.txt`, `v2-poc-after.txt`) and opened PR #11 (branch `fix/B-V2-mongo-sanitize`) linked to issue #3.

## Week 3 — V6: Password hash leak in API responses (CWE-200 / CWE-359, OWASP A01:2021)

- Confirmed the leak with a live PoC: `GET /getUser/:userId` returned HTTP 200 with the target's bcrypt hash and email, with no `Authorization` header sent. Established it was bulk-exploitable rather than a single-account issue — `controllers/post.js` populates `user` on the public post feed and Mongoose includes `_id` by default, so an anonymous caller can enumerate author ids and harvest hashes. Verified the leaked hash was live credential material with `bcrypt.compare('sample123', hash) === true`.
- Diagnosed the root cause: `const { password, ...otherdata } = user` on a Mongoose **document** reads `password` through a prototype getter, but the rest element copies only the document's own enumerable keys (`$__`, `$isNew` and `_doc`) — and `_doc` still holds every field. The strip operated on the wrong object, so the denylist silently failed open.
- Fixed in layers: an allowlist DTO (`helper/userDto.js`) as the primary control plus `.select()` on the query so the hash never enters application memory, and a `toJSON` transform on the User schema as a backstop for the ~900 lines of handlers left untouched. Argued the allowlist over a denylist because a denylist leaks any field added to the schema later — which is exactly how this bug arose. Noted that `toJSON` alone would *not* have caught it, since the broken code serialized a plain object whose `_doc` was a nested POJO.
- Updated `UserProfile.js` and `ProfileOfOtherUser.js`, which read `myprofile._doc.picture` — the frontend had coupled itself to the leaked internal shape, so the profile pages would have rendered blank without the change. Also hardened `servises/passport.js` to serialize the user id only; discovered afterwards that the OIDC migration had orphaned that file, so the change is correct but protects no live code path, and recorded that honestly rather than claiming a runtime fix.
- Wrote `backend/tests/responseLeak.test.js` (7 tests, all passing; full suite 65/65) asserting on the raw response text as well as parsed keys, since a key-level check would have missed a hash nested inside `_doc`. Separately found and repaired a merge regression: `index.js` had kept a duplicate pre-refactor middleware body that crashed the server on boot, and that dead block was the only place `mongoSanitize()` was mounted — so the Week 2 V2 sanitizer had not been running on any request, with only the zod layer still protecting `/login`. Committed as `3e5685a`, separate from the V6 branch.

## Week 4 — V5: User enumeration (CWE-204 / CWE-208, OWASP A07:2021)

- Identified three oracles on current master: `/login` returned three distinguishable messages (unregistered / Google-linked / wrong password), `/findOutUser` answered existence directly with 200-plus-user-object vs 404, and the reset page rendered the matched account's name, email and profile picture on screen for any address typed.
- Found a fourth that no amount of message-uniformity would fix: `bcrypt.compare` ran only when the account existed, so at cost 12 an unknown address returned in ~2ms against ~230ms — a 100x timing oracle (CWE-208). Closed it by comparing against a throwaway hash of the same cost on the no-account paths.
- Collapsed all three login failure branches into one `"Invalid email or password."` response, including the Google-linked case, on the grounds that a legitimate Google user is served by the OAuth button in the UI and loses nothing.
- Removed `/findOutUser` entirely rather than making it uniform — an endpoint whose sole purpose is answering "does this account exist" cannot be made safe while still answering. Rewired the reset flow to post the typed email straight to `sendResetPasswordCode`, which was already uniform from the CWE-640 work, so no functionality was lost.
- Wrote 10 regression tests comparing `status + raw body` as a single fingerprint rather than asserting on status codes, since the property under test is indistinguishability; verified 9 fail pre-fix and 10 pass after. Left `register`'s "email already exists" as documented accepted risk (fixing it requires a verification-first signup flow that would collide with V11) and raised `verifyemail.js`'s ok/not/ne responses as a follow-up.
