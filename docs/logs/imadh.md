## [CWE-613] Access tokens lived for 15 days and could never be revoked (V14)

Branch for this work: `fix/A-V14-jwt-refresh`.

- **Vulnerability:** `backend/helper/token.js` signed every JWT with whatever lifetime the caller passed, and all call sites passed `"15d"` — `register` and `login` in `backend/controllers/user.js` (pre-change lines 74 and 785), `POST /login/success` in `backend/routes/user.js` (pre-change line 173), and the `register_google` helper (pre-change line 116). No `expiresIn` default existed, so nothing stopped a long-lived token being issued. Because the JWT was self-contained and stateless, the server had **no mechanism to invalidate it**: `GET /logout` only cleared client-side cookies while the token kept working for the remainder of its 15-day window. A token captured via XSS, browser history, or a log file could therefore be replayed for up to 15 days, and neither logout nor a password change ended existing sessions. `authUser` in `backend/middleware/auth.js` additionally answered a blanket `400` for both a missing and an expired token, so a client could not distinguish an expired session from a malformed request. Mapped to CWE-613 (Insufficient Session Expiration) / OWASP A07:2021.

- **Fix applied:** Access tokens are now short-lived (`ACCESS_TOKEN_EXPIRY = "15m"` default in `backend/helper/token.js`, and the explicit `"15d"` arguments were removed at the live call sites) and session continuity is carried by **rotating refresh tokens**:
  - `backend/models/RefreshToken.js` (new) persists refresh tokens server-side with a TTL index on `expiresAt` and a unique index on `tokenHash`. Only a SHA-256 hash is stored, never the raw token.
  - `backend/helper/refreshToken.js` (new) issues a 256-bit opaque token via Node's built-in `crypto.randomBytes(64)` (not a JWT, so it carries no claims and cannot be forged), hashes it with SHA-256 before storage, and implements single-use rotation. `rotateRefreshToken` consumes the old token with an atomic `findOneAndUpdate({ tokenHash, revokedAt: null })`, which is what makes reuse impossible even under concurrent requests.
  - `backend/controllers/refreshToken.js` (new) exposes the handler for `POST /auth/refresh` (registered in `backend/routes/user.js`), returning a fresh 15m access token and the rotated cookie.
  - The refresh token is delivered in an **httpOnly, Secure, SameSite cookie path-scoped to `/auth`** (cookie helpers in `backend/helper/refreshToken.js`), used by `register`/`login` in `backend/controllers/user.js` and by `POST /login/success` in `backend/routes/user.js`.
  - `GET /logout` now revokes the refresh token server-side and clears the cookie, so logout genuinely ends the session.
  - `backend/middleware/auth.js` returns **401** (not 400) and tags the cause with `TOKEN_EXPIRED` / `TOKEN_INVALID` / `TOKEN_MISSING`, and parses the `Authorization` header strictly instead of the previous `slice(7)` which mangled any non-`Bearer ` value.
  - `client/src/helpers/interceptor.js` (new, wired in `client/src/index.js`) auto-refreshes on 401 and retries the original request, using a single-flight guard so concurrent 401s trigger exactly one exchange.
  - Chosen over the suggested approach in two deliberate ways: (a) the refresh token is stored **hashed** rather than in plaintext, so a database leak yields nothing replayable; (b) transport is an **httpOnly cookie** rather than a JSON body the SPA would have to keep in JS-readable storage, which is what keeps the credential out of reach of XSS — the exact threat that made a 15-day token dangerous.

- **Security contribution:** The maximum window in which a stolen access token is useful drops from 15 days to 15 minutes. Refresh tokens are revocable, so logout and account recovery now actually terminate a session, and a compromise is bounded to one rotation cycle. Replaying a consumed refresh token is treated as theft: every refresh token for that user is revoked, forcing re-authentication everywhere. Hashing at rest removes the database as a source of usable credentials, the httpOnly cookie removes XSS as a theft vector for the long-lived credential, and the TTL index prevents dead credentials accumulating.

- **Justification:** Verified before changing anything that the issue was real: `generateToken` had no default and every call site passed `"15d"`. Rotation is race-safe because the old token is consumed by an atomic conditional update, so two simultaneous exchanges cannot both succeed; the loser is treated as reuse. Reuse detection is the industry-standard response to a stolen refresh token and is why the whole family is revoked. The 400→401 change is a deliberate, required contract change (the task requires "expired token returns 401") and research confirmed nothing in `client/src` branched on the old 400 for auth responses, so the blast radius is limited to the new interceptor. Response shapes for `register`/`login` are unchanged apart from token lifetime, and the `id` claim that controllers read via `req.user.id` was preserved. Backend: `npm test` (`backend/tests/authRefresh.test.js`) covers the required scenarios — expired access token → 401, valid refresh cookie → new 15m token with a rotated httpOnly cookie, reused refresh token → 401 with all sessions revoked — plus an expired refresh token and a missing cookie. Client: `npm run build` passes.

- **Verified — not applicable (dead code):** `register_google` in `backend/routes/user.js` still contains a `"15d"` expiry. It is **unreachable**: it is never registered as a route, is not exported, and would throw immediately because it references `res` and `User`, neither of which is in scope. It was deliberately left untouched to keep this change set scoped, but it should be deleted or repaired separately — if it is ever wired up it would mint a 15-day token without a refresh cookie.
